# firefox-worker-reload-crash

Minimal reproduction for a **Firefox content-process SIGSEGV** that happens when a page is
reloaded while a Web Worker's script is still being compiled.

Reproduces with Playwright's bundled Firefox **153.0** (`firefox-1538`, shipped in Playwright
1.62.0) and still reproduces on **`@playwright/test@next`** (Firefox 155.0), on both **Linux x64
and macOS arm64**. Does not reproduce on any earlier Playwright Firefox build we tested.

Upstream Firefox bug: **[Bugzilla 2044428](https://bugzilla.mozilla.org/show_bug.cgi?id=2044428)**
(`Crash in [@ mozilla::dom::workerinternals::loader::WorkerScriptLoader::EvaluateScript]`, open).
Earlier Playwright report: [microsoft/playwright#42555](https://github.com/microsoft/playwright/issues/42555)
(closed as not planned — it was a draft with no attached repro; this repo is that missing repro).

## Run it

```bash
npm ci
npx playwright install firefox
npm test          # Playwright test runner
npm run loop      # standalone loop, no test runner
```

Expected on Firefox 153:

```
[repro] session 1 CRASHED crashed=true page.reload: Page crashed
...
[repro] DONE crashes=8/8
```

With `DEBUG=pw:browser` the underlying signal is visible:

```
[Parent NNNNN, IPC I/O Parent] WARNING: process NNNNN exited on signal 11: \
  file ipc/chromium/src/chrome/common/process_watcher_posix_sigchld.cc:161
```

## What the page does

That's the whole thing — there is no framework, no bundler and no build step:

```js
window.__worker = new Worker("/worker.js");   // worker.js is ~2 MB of plain functions
window.__ready = true;                        // deliberately NOT waiting for the worker
```

The test then calls `page.reload()` as soon as `__ready` is set, so the reload tears the worker
down while the JS engine is still compiling its script.

## What is and isn't required

Required:

- A **Web Worker**. A ~7 MB script loaded on the main thread via `<script src>` instead never
  crashed (0/4) — the worker is essential, not merely the parse cost.
- A **large enough worker script**, so that compilation is still running when the reload lands:

  | `WORKER_MB` | crashes |
  |---|---|
  | 0.25 | 0/4 |
  | 0.5 | 0/4 |
  | 0.75 | 2/4 |
  | 1 | 4/4 |
  | 2 | 6/6 |
  | 7 | 4/4 |

- Reloading **immediately**, while the worker is still starting.

Not required: `postMessage` to the worker (`POST=0` still crashes 4/4), Monaco, TypeScript,
a bundler, module workers, multiple tabs, or any settle delay. An earlier draft of this repro
used Monaco's `ts.worker` and a 4 s settle timeout; the settle delay made it *less* reliable,
and Monaco turned out to be irrelevant.

## Version bisect

Same repro, walking every Firefox build Playwright shipped during the 1.62 cycle
(Hetzner ccx23, dedicated 4 vCPU, Ubuntu 24.04.4, Node 22, headless):

| Playwright | Firefox build | Firefox version | crashes |
|---|---|---|---|
| 1.61.1 | `firefox-1532` | 151.0 | 0/8 |
| 1.62.0-alpha-2026-06-17 | `firefox-1532` | 151.0 | 0/8 |
| 1.62.0-alpha-2026-06-18 | `firefox-1533` | 151.0 | 0/8 |
| 1.62.0-alpha-2026-07-08 | `firefox-1534` | 152.0.4 | 0/8 |
| 1.62.0-alpha-2026-07-17 | `firefox-1535` | 152.0.4 | 0/8 |
| 1.62.0-alpha-2026-07-20 | `firefox-1536` | 152.0.4 | 0/8 |
| **1.62.0-alpha-2026-07-23** | **`firefox-1538`** | **153.0** | **7/8** |
| 1.62.1 | `firefox-1538` | 153.0 | 8/8 |

The boundary is the `firefox-1536` → `firefox-1538` browser roll. The two nightlies either side
of it are three days apart, so the Playwright-side code is effectively identical — this is the
browser roll, not a Juggler change. `firefox-1537` was never published to npm.

### Still present on `@playwright/test@next`

| Platform | Playwright | Firefox | crashes |
|---|---|---|---|
| Linux x64 | 1.61.1 | 151.0 (`firefox-1532`) | 0/8 |
| Linux x64 | 1.62.1 | 153.0 (`firefox-1538`) | 8/8 |
| Linux x64 | 1.64.0-alpha-2026-09-04 (`@next`) | 155.0 (`firefox-1543`) | **6/6** |
| macOS 26.6.1 arm64 | 1.61.1 | 151.0 (`firefox-1532`) | 0/6 |
| macOS 26.6.1 arm64 | 1.62.1 | 153.0 (`firefox-1538`) | 6/6 |
| macOS 26.6.1 arm64 | 1.64.0-alpha-2026-09-04 (`@next`) | 155.0 (`firefox-1543`) | **6/6** |

So this is **not Linux-only and not fixed** — it still reproduces on the current nightly with
Firefox 155, on both Linux x64 and macOS arm64, and the 151 → 153 boundary is the same on both.

**This is an exposure shift, not necessarily a new bug in 153.** Mozilla crash-stats shows the
`WorkerScriptLoader::EvaluateScript` signature across 152.0a1, 152.0.x, 153.0.x, 154.x and
155.0a1 (175 reports since 2026-03-01, 173 of them content-process), so the underlying race
predates Firefox 153. What changed in the 153 build is that it became reliably reproducible.

## Crash details

Core dump from the content process (`MOZ_DISABLE_CONTENT_SANDBOX=1` so a core is written):

```
Core was generated by `firefox -contentproc -isForBrow'.
Program terminated with signal SIGSEGV, Segmentation fault.
Crashing thread name: "DOM Worker"

=> 0x...274400:  mov 0x8(%rdi),%rax
   0x...274404:  mov 0x10(%rax),%rax
   0x...274408:  ret

si_addr = 0x8
rdi     = 0x0        <-- null this-pointer
```

A plain null-pointer dereference on the **DOM Worker** thread. `libxul.so` in the Playwright
build is fully stripped (no dynamic symbols), so frames symbolize only as offsets;
`libxul.so` base was `0x755202800000`:

```
#0  libxul+0x6a74400
#1  libxul+0x6a52070
#2  libxul+0x6a51c01
#3  libxul+0x6a5487f
#4  libxul+0x6a54915
#5  libxul+0x6a751a4
#6  libxul+0x3d51e6c
#7  libxul+0x3d5559a
#8  libxul+0x6a6fce5
#9  libxul+0x6a73e65
#10 libxul+0x6a55139
#11 libxul+0x6a54d91
#12 libxul+0x6a7e2bd
```

This is consistent with the root cause analysed in Bugzilla 2044428: `ProcessPendingRequests()`
removes the request before `EvaluateScript()` runs, so `AllScriptsExecuted()` returns true
mid-evaluation, and a re-entrant `TryShutdown()` (reached from inside `JS::Compile()` via a GC →
cycle collector → microtask checkpoint → interrupt callback → `NotifyInternal(Canceling)`) nulls
`mWorkerRef` underneath the still-running `EvaluateScript`. The size threshold above is what that
predicts: the script has to be big enough for a GC to happen mid-compile and for compilation to
still be in flight when the reload cancels the worker.
